# Archive Browser

A local-first desktop browser for macOS, Windows, and Linux that automatically saves a durable, searchable, offline copy of every page you actually visit — no account, no cloud service, nothing sent anywhere except one disclosed exception: a periodic, on-by-default check against GitHub Releases for a newer version (see "Auto-update").

Current version: **0.3.3** — see [Version history](#version-history) for what changed in every release.

## Why

Normal browser history is a list of URLs, not the pages themselves. Pages change, go offline, or end up behind logins you no longer have. Archive Browser captures what you actually saw — a full-page screenshot, the complete MHTML snapshot, and the extracted text — at the moment you visited, and keeps it on your disk, in a format you can open years later with no network connection.

## Two kinds of archiving

Archive Browser saves pages in two complementary ways:

1. **Automatic per-page capture** (always on, in the background). Every page you visit is saved to the local Library as MHTML + full-page screenshot + extracted text, catalogued in SQLite. This is the "never lose a page you looked at" layer.
2. **"Capture the Page" → a portable `.sitearchive` file** (explicit, on demand). Captures the current page — or the whole website — into a single self-contained file you can move, back up, or send to someone else, and browse offline as though it were still live.

The rest of this README covers both; the `.sitearchive` feature is described in its own section below.

## Library search: ranking and snippets

The Library's search box (`archives_fts`, an FTS5 index over every archived page's title, URL, domain, and extracted text — kept in sync by [`ArchiveRepo`](src/main/db/archiveRepo.ts) rather than by triggers, since text extraction finishes asynchronously after the initial row) used to only filter: a query either matched or it didn't, and matches came back in whatever order the active sort (newest/oldest/domain/size) happened to put them in — a title match and an incidental mention buried in body text looked identical.

- **Results are now ranked by relevance**, not the sort dropdown, the moment a search term is present: `ORDER BY bm25(archives_fts, 0.0, 2.0, 1.0, 1.0, 1.0)`, weighting a title match twice a body match (a term appearing in the title is a stronger signal than the same term somewhere in a page's extracted text). The sort dropdown is hidden while searching — replaced with a plain "Sorted by relevance" note — rather than silently ignoring a selection that would otherwise look like it should still be doing something.
- **Each result carries a plain-text snippet** built from FTS5's own `snippet(archives_fts, -1, ...)`, with `-1` picking whichever indexed column the match actually landed in (title, URL, domain, or body) rather than assuming it's always body text. The matched span is marked with two Unicode marker characters (`SNIPPET_MARK_START`/`SNIPPET_MARK_END` in [`shared/types.ts`](src/shared/types.ts)) — not embedded HTML — so the renderer highlights it by splitting on those markers and wrapping the match in `<mark>`, without ever needing to trust or sanitize markup coming out of the database.
- An archive predating this feature, or one with no extracted text yet, still searches and browses normally — it just ranks and highlights on whatever FTS already has indexed for it, same as before.

## Whole-library export and import

Per-archive export already existed (one page → one zip). Settings → Data now also has **Export whole library…** / **Import whole library…**, for migrating every archived page — or backing the whole Library up — in one file, via [`libraryTransfer.ts`](src/main/library/libraryTransfer.ts).

- **A whole-library export is its own zip format**, not a bundle of per-archive exports: one `library-manifest.json` at the root (every active archive's catalog row — title, URLs, domain, status, warnings, tags, per-file SHA-256 hashes — read straight from the database, which is the actual source of truth, not scanned off each archive's on-disk `metadata.json`, since a failed/skipped capture can have a DB row with no directory at all) plus each archive's actual content files under `archives/<id>/`. `hasMhtml`/`hasScreenshot`/`hasText`/`hasFavicon` in the manifest reflect a file **actually found on disk at export time**, not just what the DB row claims — a stale claim would otherwise promise bytes the zip never contained.
- **Importing treats the zip as untrusted input**, the same posture `.sitearchive` reading already takes: entry names are validated the same way (traversal, absolute paths, zip-slip), with per-entry and whole-export size caps and a compression-ratio check against zip bombs (`openZip`/`readEntryBuffer`/`safeEntryName` are shared with [`archiveReader.ts`](src/main/sitearchive/archiveReader.ts) rather than reimplemented). Every manifest entry is shape-validated field by field before anything is inserted — a malformed field (wrong type, an unrecognized `status`) would otherwise still serialize into `warnings_json`/`tags_json` without error and only break on a later read, so it's rejected up front instead. Each content file's bytes are verified against the manifest's recorded SHA-256 before being written; one that fails is simply dropped (with an `import-content-missing` warning attached to that archive) rather than aborting the whole entry, and one archive entry failing outright doesn't abort the rest of the import.
- **Already-present archives are never overwritten.** `id` is the catalog's primary key, so an id already occupying a row at the destination — even a soft-deleted one — is always skipped, never re-inserted; re-importing the same export twice is safe and just skips the second time. This makes the feature additive/idempotent by construction: there is no merge or replace option, by design, since the two use cases this exists for (migrating to a new machine, restoring a backup) never actually need one.
- **Nothing exported is trusted verbatim on the way back in.** `faviconPath` is never carried across — it's an absolute path only meaningful on the machine that wrote it — it's recomputed from whether a favicon file actually came through in this import. Extracted text is re-read from the verified `text.txt` bytes and re-indexed into the destination's FTS table (`updateExtractedText()`), so a migrated library is searchable immediately, not just browsable.
- Files are staged and atomically renamed into place per archive (`withStagedArchiveDir()`, the same helper a live capture uses) before that archive's DB row is inserted — so an import killed partway through never leaves a half-written directory passing as a real archive.

## Architecture overview

Three trust tiers, three sessions/partitions:

1. **Trusted chrome** — a single `BrowserWindow` running the React UI (tabs, address bar, Library, Settings). `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, a strict `Content-Security-Policy`, and one narrow `contextBridge` preload ([src/preload/trusted-preload.ts](src/preload/trusted-preload.ts)) exposing only typed, `zod`-validated IPC calls.
2. **Live browsing** — one `WebContentsView` per tab (Electron's current recommended primitive for embedding web content, replacing the deprecated `BrowserView` and the discouraged `<webview>` tag), attached as a child view of the trusted window's `contentView`. Sandboxed, no preload, session partition `persist:browsing` shared across normal tabs (so cookies/logins persist), or a unique in-memory partition per private tab.
3. **Offline archive viewer** — another `WebContentsView`, on a dedicated session whose `webRequest` handler denies every request except our own `archive://` protocol (screenshot/text/fallback content) and a `file://` path scoped to the archives root (the MHTML snapshot itself — see the note on MHTML below), with JavaScript disabled by default (`javascript: false` in `webPreferences`).

No preload script is ever attached to a browsing or offline-archive `WebContentsView` — page content has no path to `ipcRenderer`, Node, or Electron internals, directly or indirectly, regardless of what the page's own script does.

**Capture pipeline** ([src/main/capture/captureService.ts](src/main/capture/captureService.ts)): on a top-level navigation (`did-navigate`, main frame only), a debounced settle timer (default 3s, configurable) fires, then the page is snapshotted — `webContents.savePage(..., 'MHTML')`, a full-page PNG via the Chrome DevTools Protocol (`Page.captureScreenshot` with `captureBeyondViewport: true`, since `capturePage()` alone only grabs the viewport), and extracted visible text (host-initiated `executeJavaScript`, form/password values stripped before serialization). SPA route changes (`did-navigate-in-page`) are debounced and filtered so hash-only changes aren't treated as new visits. Writes go through a staging directory and are `rename()`d into place only on success — a crash mid-capture can never leave a half-written archive in the catalog.

**Storage layout**:

```
archives/
  <archive-id>/       # UUID, never derived from user input
    page.mhtml
    screenshot.png
    text.txt
    metadata.json
```

SQLite (`better-sqlite3`, with an FTS5 index for search) is the catalog; the files on disk are the source of truth. Re-visiting a URL creates a new archive row grouped by `canonical_url`, never an overwrite.

**Per-page capture integrity.** Each of `page.mhtml`, `screenshot.png` and `text.txt` gets a SHA-256 recorded in the catalog at the moment it's written ([captureService.ts](src/main/capture/captureService.ts)), and every one is verified again before its bytes are shown, the same principle the `.sitearchive` container already applies to its own entries. `screenshot.png`/`text.txt` are verified inline in [the `archive://` protocol handler](src/main/offline/offlineProtocol.ts) — a mismatch returns an error response instead of the file. `page.mhtml` can't be checked that way (it's loaded via `loadFile()`, not `archive://` — see below), so it's read and hashed once, up front, right before that load; a mismatch is treated exactly like a missing MHTML and routes to the same screenshot/text fallback page, now naming the reason ("this page failed an integrity check") rather than the generic "could not be rendered faithfully". Archives captured before this column existed have `NULL` hashes and are shown without verification, the same convention the `.sitearchive` reader uses for an entry the manifest never hashed.

**A disclosed exception to "prefer a custom protocol over `file://`":** the offline viewer's MHTML snapshot is loaded via `loadFile()` on a path built by [`archiveFilePaths()`](src/main/util/paths.ts) (never attacker- or page-influenced), not through `archive://`. This was empirically verified during development: Chromium's MHTML document loader only recognizes a document as MHTML when it's fetched via `file:` (or a small set of built-in schemes) — serving the identical bytes with an identical `multipart/related; boundary=...` `Content-Type` through our own `protocol.handle()` response is accepted at the network layer but Chromium still fails it with `ERR_FAILED` before it ever reaches the MHTML renderer. [`offlineSession.ts`](src/main/offline/offlineSession.ts)'s `webRequest` denylist independently re-validates that the one `file://` request it allows resolves inside the archives root, on top of the caller-side validation, so this doesn't reopen arbitrary filesystem access — it's `loadFile()` given one specific, pre-checked path, on a session with no other network access and JavaScript disabled. Screenshot, extracted text, and the no-MHTML fallback page are all still served through `archive://` as originally designed.

### Threat model (summary)

| Concern | Mitigation |
|---|---|
| Malicious website in a tab | sandbox + no preload + `nodeIntegration: false`; can't reach Electron/Node; can't navigate the trusted window (`will-navigate` guard on the trusted `BrowserWindow`); popups routed through our own validated tab-creation, never raw `shell.openExternal` on unvalidated input |
| Path traversal via archive IDs | IDs are server-generated UUIDs only; every filesystem path is built via [`archiveDirFor()`](src/main/util/paths.ts), which validates the ID and verifies the resolved path stays under the archives root |
| Unsafe/unvalidated IPC | Every `ipcMain.handle` call checks `event.sender.id` against the trusted window and validates arguments against a `zod` schema in [ipcContract.ts](src/shared/ipcContract.ts) before doing anything |
| Archive tampering | Atomic staged writes (temp dir → rename); UUIDs prevent cross-archive collision via the UI. SHA-256 recorded per file at capture time (`mhtml_sha256`/`screenshot_sha256`/`text_sha256` in the catalog), verified on every read — `archive://` refuses to serve a mismatched `screenshot.png`/`text.txt`, and the offline viewer falls back rather than loading a tampered `page.mhtml` (see "Per-page capture integrity" below) |
| Credential leakage into archives | Cookies/localStorage/session tokens are never read into archive files; password `<input>` values are stripped before text extraction; MHTML capture is the browser's own same-origin snapshot, not a credential export |
| Unwanted network during offline viewing | Enforced at the session/`webRequest` layer, not just by omitting scripts — even a hypothetical future JS-enabled mode would still hit the denylist |
| Certificate errors | Never overridden/ignored — default Chromium verification behavior is left intact |

## Portable website archives (`.sitearchive`)

Click **Capture the Page** in the toolbar (or File ▸ Capture the Page…, `Cmd/Ctrl+Shift+S`) and choose a scope:

- **Current page only** — this page plus everything it needs to display.
- **Entire current website** — follows links on the same origin, recursively, within safe default limits (depth 3, 50 pages, 256 MB).
- **Custom scope** — max depth, max pages, max archive size, additional allowed domains, explicitly-included external domains, paths to always include even if they'd otherwise be skipped as non-content (e.g. `/search`), whether to include documents or audio/video, crawl delay, and concurrency.

**Removing the limits.** In Custom scope, leaving a limit field blank means *no limit*, and a **Remove all limits** button clears all three at once. Unlimited captures require ticking the confirmation, because on a large site they can run a long time and produce a very large file. Two things still hold regardless: **Pause and Cancel work throughout**, and a **free-disk-space floor (500 MB) is enforced and cannot be bypassed** — the capture stops itself and records the reason rather than filling your drive. Finite values are still clamped to sane ceilings (depth 25, 50,000 pages, 64 GB) so a typo can't become an accidental multi-day crawl; only an explicitly blank field is truly unbounded. Request concurrency is never bypassable, since that limit protects the site being captured rather than your disk.

Anything beyond the recommended limits requires an explicit confirmation before it will start. During capture you get a live progress bar, an elapsed clock, and pages-discovered / pages-saved / current-URL / downloaded-size / warning / failure counts, plus **Pause** and **Cancel**.

### Which pages a budgeted crawl spends itself on

A page limit forces a choice about *which* pages get captured, and the obvious answer is wrong. A plain FIFO queue makes the crawl strictly breadth-first, which sounds even-handed but lets a single link-dense page own the entire budget.

This was reported against a real forum and it is severe. `rangerovers.net`'s front page yields **86 in-scope links** — 37 forum sections, 21 member profiles, 22 utility pages (`/login`, `/register`, `/search`, …) and only 5 threads. Threads otherwise live one level below, inside section pages. Breadth-first with the default 50-page budget therefore captured section and navigation pages until the budget ran out and archived **zero threads** — the entire reason someone captures a forum.

Two changes fix that, neither of them site-specific:

- **The frontier is rotated across the page that discovered each link** ([crawlFrontier.ts](src/main/sitearchive/crawlFrontier.ts)), taking one item per discovering page per turn instead of draining an entire level first. As soon as a section page is captured, the threads it found interleave with the sections still queued. Order within one page's links stays document order. On the forum fixture this takes a 25-page capture from 0 threads to 9.
- **Account, search and navigation routes are skipped** (`looksNonContent()`), because they are not archivable content and every one captured is a thread not captured. Each skip is recorded as a `skipped-non-content` failure so it is visible in the archive rather than silent.

**A single page cannot stall the crawl.** Navigation has a timeout and each resource fetch has one, but the capture phases had no collective limit — so one pathological page could hold a crawl open indefinitely. Measured on a real forum photo thread (116 images, 27 dead third-party image hosts, heavy ad tags): **over 15 minutes on one page without finishing.** Each page now gets a two-minute wall-clock budget; when it runs out, remaining resource fetches and per-element image fallbacks are abandoned, the shortfall is recorded as a warning, and the durable fallbacks (full-page screenshot and extracted text) are still captured. Per-phase timings are logged for every page, including pages that fail or blow the budget — which is exactly when they matter.

**Skips are recorded once per URL, not once per link.** A "Log in" link in a site's global navigation is seen on every page crawled, and skips are decided before the enqueue dedupe — so without a guard of their own each records an identical failure entry per page, burying real failures. Skip kinds also get a per-kind ceiling (500) below the manifest's global 5,000, so they can never crowd genuine fetch failures out of the list.

**Hitting a limit is now recorded in the archive**, as a `stopped-at-limit` failure naming how many discovered pages were left uncaptured. Previously a budget-truncated capture was indistinguishable from a complete one, which is exactly how a forum capture that reached no threads still looked like a success.

The bar is measured against *pages discovered so far*, which is the only honest denominator mid-crawl — the true total isn't knowable up front, and finding new links legitimately makes the bar recede. While the archive is being zipped there's no countable unit, so that phase shows an indeterminate bar rather than a fabricated percentage. On completion you get the saved location, page and asset counts, final file size, a list of anything that failed, and **Open Archive** / **Reveal in Finder** (or **Show in File Explorer**) / **Retry failed pages**.

### Parallel crawling

`scope.concurrency` (1–6, the Custom scope dialog's "concurrency" field) is the number of independent workers [`CaptureJob`](src/main/sitearchive/crawler.ts) runs at once, each against its own hidden `WebContentsView`, pulling from the same crawl queue. `crawlDelayMs` is the politeness delay *a single worker* waits between its own page loads — so with `concurrency: 4`, the aggregate request rate against the target site scales with concurrency, the same as four polite visitors browsing at once rather than one visitor browsing four times faster.

Making an already-tested sequential crawl loop run N workers deep meant finding every place shared, mutable crawl state assumed only one page was ever in flight:

- **`maxPages` had to become an atomic claim, not a check-then-act read.** Two workers each checking "have we completed the limit yet?" and only afterward claiming a page can both pass the check before either finishes — which is exactly what let a 2-worker, 3-page-limit capture complete 4 pages during development. The fix tracks `pagesCompleted + pagesInFlight` and claims a slot synchronously (no `await` between the check and the claim), the same pattern used below for `SiteArchiveBuilder`. A page that fails releases its claimed slot rather than counting against the budget, matching the original single-worker behavior.
- **`SiteArchiveBuilder.addAsset`/`addResponse` had a real race**, exposed rather than introduced by this change: two workers storing byte-identical content at the same time (a shared logo fetched from two different pages) would both miss the dedup cache, both write the same file path concurrently (a real risk of a torn write for a large asset), and one caller's `sourceUrl` could be silently lost. Fixed with an in-flight-write guard — a second caller for a hash already being written awaits the first caller's write instead of racing it. Tested directly at the unit level (`Promise.all` of two concurrent `addAsset` calls for identical bytes, which a sequential `await` would never have exercised) and via a real concurrent crawl end-to-end (`tests/e2e/sitearchive-parallel.spec.ts`).
- **View recycling became per-worker.** Each worker gets its own screenshot-degradation streak and its own page-count-since-recycle, since both are about *that worker's own renderer process* looking wedged or having grown — a different worker's renderer is a different process, unaffected. One deliberate behavior change: recycling no longer clears the shared browsing session's HTTP cache, since that session is shared across every worker (same login/cookies for the whole crawl) — clearing it from one worker's recycle would evict other workers' still-useful cached responses and disrupt whatever they currently have in flight.
- **Everything else** — the queue (`CrawlFrontier`), `queuedOrDone`, the running byte/page/warning counters, the crash-recovery journal — turned out to already be safe: either fully synchronous (no `await` between a check and the mutation that follows it) or, for the journal, already order-independent per URL on replay.

Verified end-to-end (`tests/e2e/sitearchive-parallel.spec.ts`): capturing the same page budget at `concurrency: 4` completes in meaningfully less wall-clock time than `concurrency: 1` against the identical fixture, and a 6-worker capture over a site with a cross-page duplicate asset (identical bytes under two different URLs, so the dedup path is actually exercised rather than trivially satisfied by every page using one canonical URL) still produces exactly one stored asset with both source URLs intact.

### The file format

A `.sitearchive` is a **ZIP container with a documented layout** — not a proprietary blob. Rename it to `.zip` and inspect it with any standard tool:

```
manifest.json          # format version, URLs, scope, page list, route map,
                       # failures, content types + SHA-256 checksums, app
                       # version, total uncompressed size
pages/<pageId>.html    # serialized rendered DOM (not the original server HTML)
pages/<pageId>.txt     # extracted searchable text
assets/<sha256>.<ext>  # content-addressed, so a shared logo is stored once
screenshots/<pageId>.png
responses/<sha256>.json # safe captured GET responses
index.sqlite           # queryable catalog of everything above, plus an
                       # FTS5 index (pages_fts) over every page's title
                       # and extracted text for in-app search
```

Writes are atomic: everything is staged in a temp directory, zipped to `<name>.tmp-<uuid>`, and only renamed to the final `.sitearchive` after the capture and validation both succeed. A cancelled or crashed capture therefore can never damage an existing archive at that path.

### Surviving an interrupted capture

Writing the archive only at the end is what makes a half-written file impossible — but on its own it also means a crawl that dies at minute 150 produces *nothing*, which is exactly what happened to a 151-minute, 810-page, 2.6 GB capture of `landrover.ca`.

Every captured byte was already on disk in the staging tree. What died with the process was the bookkeeping held in memory: which pages exist, which assets dedupe to which hash, the route map, and the crawl queue. So that bookkeeping is now journalled to disk as it is produced ([captureJournal.ts](src/main/sitearchive/captureJournal.ts)) — an append-only `checkpoint.jsonl` beside the staged files, plus a small metadata sidecar recording the start URL, scope and chosen output path.

The ordering rule the design rests on: **bytes are written to the staging tree first, and the journal record is appended only after that succeeds.** A crash can leave a file the journal never mentions, which is harmless because the manifest is the authority and unlisted entries are ignored — but never a journal record naming a file that isn't there. Records are `await`ed rather than buffered, since buffered writes lost to a kill would be precisely the ones describing the most recent work. Replay tolerates a truncated final line, which is what a process killed mid-append leaves behind.

An interrupted capture can then be:

- **finished as it stands** (`finalizeRecoveredCapture()`) — a valid, checksum-consistent `.sitearchive` holding the pages that were captured, with a failure entry recording that it stopped early so it can never pass as complete; or
- **resumed** (`CaptureManager.resumeInterrupted()`) — the crawl continues from the pending queue, re-capturing nothing. A resumed run keeps the original archive id, because that id is baked into the `archive-site://<archiveId>` URLs already serialized into every page captured before the interruption; or
- **discarded** (`discardRecoveredCapture()`) — the staging tree and everything captured in it are deleted for good.

A capture that *fails* (as opposed to being cancelled) now keeps its staging tree rather than deleting it, since that tree is recoverable work. Cancelling still discards everything, because the user asked for that.

**Surfaced in the UI as a startup prompt.** Once per launch, before any tab is created, the trusted window checks for recoverable captures (`captureRecovery:list`) and — if any exist — shows a dialog naming each one (start URL, pages captured so far, failures, bytes on disk, where it will be saved) with Resume / Finish / Discard actions. Finish only appears when at least one page was captured (finishing an empty crawl would produce an archive `openSiteArchive` itself refuses to open); Discard asks for confirmation inline before it removes anything. Resume and Finish both reuse the exact main-process functions above — the dialog is a thin display and confirmation layer, not a second implementation of the recovery logic — and Resume's progress is reported through the same live-progress channel and dialog an ordinary capture uses, so a resumed crawl looks and behaves like any other. Dismissing the prompt ("Not now") leaves the capture exactly as it was; since nothing was resolved, it is offered again the next time the app starts. Each staging directory also carries a pid lock while its journal is open, so a capture actually running right now — in this instance or another one sharing the OS temp directory — is never offered as recoverable in the first place, and Resume/Finish/Discard all refuse it defensively even if the UI's list happens to be stale.

Staging directories are also swept on startup (`sweepSiteArchiveStaging()`). A cancelled or failed capture cleans up after itself, but a *killed* process never runs its cleanup, and the staging tree for a large crawl is gigabytes — six such directories totalling 3.8 GB were found left behind by real runs. The sweep skips any directory written to within the last hour, judged by the mtimes of its subdirectories rather than the parent, so it can never delete the staging tree of a capture that is still running in another instance. It also spares checkpointed trees for a full week, so the fix for leaked staging directories can never quietly delete a crawl that died overnight and is still recoverable.

Double-clicking a `.sitearchive` opens it in Archive Browser on macOS, Windows 11, and Linux (registered via `fileAssociations` in [electron-builder.yml](electron-builder.yml); delivered by the `open-file` event on macOS and via argv/`second-instance` on Windows and Linux).

### Per-page memory telemetry

A 151-minute unlimited capture once died mid-run with no crash report and nothing logged for the whole run (see Known Limitations) — diagnosing that after the fact meant manually estimating the archive builder's in-memory bookkeeping, which turned out not to be the cause. [`memoryTelemetry.ts`](src/main/capture/memoryTelemetry.ts) exists so the *next* long crawl leaves an actual trend behind it instead of requiring that again.

Every page's existing `sitearchive.page_timings` log line now also carries `mainRssBytes`/`mainHeapUsedBytes` (the main process, where the builder's bookkeeping lives), `rendererBytes`/`rendererPeakBytes` (the crawling `WebContentsView`, matched by OS pid via `app.getAppMetrics()` — a separate process from Electron's point of view, and the untested suspect), and `systemFreeBytes`/`systemTotalBytes` (`os.freemem()`/`os.totalmem()` — whole-machine memory, not just this process's own RSS). That last pair closes a real gap: a kernel out-of-memory kill is an unblockable `SIGKILL` with no crash report and nothing an in-process handler ever sees, which is exactly what the original 151-minute crash looked like, and per-process RSS alone can't distinguish "this process grew" from "the whole machine was starved by something else" (another renderer, the GPU process, `/dev/shm`) — whole-machine free memory can. This adds fields to a line that was already logged once per page; it doesn't add new log volume on its own. `recycleView()`'s existing `sitearchive.recycling_view` line gets the same readings taken immediately before the view is torn down, which is the first actual measurement of whether recycling reclaims the memory its own docstring says it does. The pid-matching logic (`findRendererMemory`) is pure and unit-tested; the sampling itself needs a real multi-process Electron app and is exercised implicitly by every e2e capture test.

Separately, navigation now distinguishes a renderer that died mid-load (crash, or Chromium's own out-of-memory kill) from an ordinary failure: `loadUrl()` ([crawler.ts](src/main/sitearchive/crawler.ts)) previously only listened for `did-finish-load`/`did-fail-load`/`did-redirect-navigation`, so a renderer killed mid-navigation fired none of them — the promise just sat until the 30-second page-load timeout and got recorded as a generic `timeout`, silently discarding the one signal (`render-process-gone`'s `reason`: `oom`, `crashed`, `killed`, ...) that could have named the actual cause. It now resolves immediately with a new `render-process-gone` failure kind carrying that reason, is retryable via "Retry failed pages" like any other transient failure, and forces that worker's view to be rebuilt before its next page rather than reusing a `WebContentsView` whose underlying OS process is already gone. Unit-tested (`tests/unit/loadUrl.spec.ts`, using a plain `EventEmitter` in place of a real `WebContents` since `loadUrl` only ever calls `on`/`removeListener`/`loadURL`/`stop` on it) and typechecked clean.

This is still diagnostics and a blind-spot fix, not a resolution — the 151-minute crash has not recurred or been reproduced in this environment, so whether the renderer process, the whole machine running out of memory, or something else entirely was the actual cause is still an open question. But the next occurrence now has three things the original one didn't: a memory trend across both processes, whole-machine free memory alongside it, and — if a renderer process actually died rather than the whole app — a named reason on the page it happened to, instead of an indistinguishable timeout.

### Reading an archive safely

A `.sitearchive` is a portable file people will share, so it is treated as untrusted input. Before any entry's bytes are used ([archiveReader.ts](src/main/sitearchive/archiveReader.ts)):

| Threat | Defence |
|---|---|
| Path traversal (`../`, absolute, UNC, `C:\`, backslash, NUL) | Entry names normalized and rejected by `safeEntryName()`; manifest-referenced paths validated too, so a hostile manifest can't point outside the container either |
| Zip bomb | Per-entry and whole-archive uncompressed size caps, plus a compression-ratio cap that rejects absurd expansion **before** decompressing |
| Oversized archive | Entry-count cap and a 4 GB total-uncompressed cap |
| Tampering / corruption | Every entry's SHA-256 is verified against the manifest before its bytes are served |
| Smuggled extra files | Entries not listed in the manifest are ignored entirely — the manifest is the authority |
| Wrong/newer format | Manifest shape is validated field by field; a newer `formatVersion` is refused with a clear message |

### Browsing an archive offline

Archives open in a dedicated session where **all network access is blocked at the session layer** — only the custom `archive-site://` protocol resolves. That's a structural guarantee, not a promise about page content: an archived page cannot reach the internet even if it contains scripts that try. On top of that, `fetch`/`XHR`/`WebSocket` are neutralized in-page, service worker registration is disabled, Node integration stays off, context isolation and sandboxing stay on, no preload is attached, and a persistent **Offline Archive** indicator is shown while you're in one.

Links are rewritten at serve time (once the crawl's route map is complete, so a link captured on page 1 to a page discovered later still resolves):

- Target **in the archive** → opens the archived page. Back, forward, refresh, fragments, query strings, and relative links all behave normally.
- Target **not captured** → an explicit offline page naming the URL, with an **Open Live Version** button that confirms before leaving the archive.
- **Downloadable files** captured in the archive open the local archived copy.
- `mailto:`, `tel:`, custom protocols → explicit confirmation. **Executables are refused outright.**
- Forms are read-only; `POST`/`PUT`/`PATCH`/`DELETE` are never captured and never replayed.

### Searching inside an archive

The 🔍 button in the toolbar (visible only while viewing an archive tab) searches every captured page's title and extracted text, using the FTS5 index already shipped inside `index.sqlite` (see "The file format" above) rather than decompressing and scanning every `pages/<id>.txt` file at query time. Results show as you type (debounced), each with a plain-text excerpt around the match; clicking one navigates the current archive tab straight to that page.

Two things worth knowing about how this is built:

- **The FTS index is populated once, at the end of a capture, from the same text already written to `pages/<id>.txt`** — not held in memory for the whole crawl. `writeIndexDatabase()` re-reads each page's `.txt` file off disk right before zipping, which is the one place that needs the extracted text again after `addPage()` writes it; keeping it in memory for a 50,000-page unlimited capture would not be free.
- **`index.sqlite` is extracted to a temp file, not queried in place**, because better-sqlite3 (like SQLite generally) has no API for opening a database directly out of an in-memory buffer or a file still sitting inside a ZIP. The temp file is named deterministically from the archive's id, so re-opening the same archive overwrites it rather than accumulating a new one, and it's checksum-verified (via the same `readEntry()` every other manifest-listed file goes through) and deleted when the archive is closed. An archive from before this feature existed, or one with a corrupt/missing catalog, still opens and browses normally — search on it just returns no results rather than the whole archive failing to open.

### Resume-only retry

"Retry failed pages" (in the capture progress dialog, once a capture finishes with failures) used to just reopen the scope dialog and start an entirely new capture from scratch — re-fetching every page, including the ones that already succeeded. [`retryFailedPages.ts`](src/main/sitearchive/retryFailedPages.ts) instead re-attempts only the failures, merging the result back into the same archive.

- **What counts as retryable.** `retryableFailures()` keeps only genuine page-attempt failures (`fetch-failed`, `http-error`, `timeout`, `too-large`, `redirect-loop`, `render-failed`, `serialize-failed`, `interrupted`) — never the intentional skips (`skipped-scope`, `skipped-non-content`, etc.) that a fresh crawl would make the exact same call on again, and never asset-level or administrative entries. A URL recorded as failed more than once, or under two forms that normalize to the same page, is retried once.
- **Everything that already succeeded is kept, not re-fetched.** `SiteArchiveBuilder.restoreFromManifest()` seeds a fresh builder straight from the already-finalized archive's manifest — pages, assets, responses, routes, and the remaining (non-retried) failures — after the corresponding staged bytes are copied back onto disk from the archive. Only the previously-failed URLs are actually navigated to again, reusing the exact same navigation/timeout/redirect-loop handling a fresh crawl uses (`loadUrl()`, exported from `crawler.ts` for this reason rather than duplicated).
- **The original archive is never at risk.** A retry writes to a new staging tree and only replaces the original file via the same atomic `fs.rename` every capture's `finalize()` already uses — so a crash mid-retry leaves the original `.sitearchive` completely untouched.
- **Reuses the existing progress UI**, rather than a second dialog: `CaptureProgress`/`CaptureResult` gained a `kind: 'capture' | 'retry'` field, and `CaptureProgressDialog` branches on it for wording ("Retrying failed pages…", "Pages to retry" vs "Pages discovered", etc.) — everything else about how progress is reported and rendered is identical to a normal capture.

**Not e2e-verified in this environment.** Unit coverage is solid (`retryableFailures`/`inferDepth`/`restoreFromManifest`, 10 tests) and `npm run typecheck` passes clean, but a dedicated end-to-end test (`tests/e2e/sitearchive-retry.spec.ts`) could not be confirmed passing here: this sandbox became too resource-strained mid-session to trust the result — even an unrelated, already-passing e2e test and a plain `vitest run` both failed with worker-process crashes (`SIGSEGV`)/hangs unrelated to this feature's code, traced to a root `unattended-upgrade` process pegging a CPU core alongside very low free memory. One real bug *was* found and fixed along the way: the test fixture's simulated broken page originally redirected to itself, which crashed the whole Electron app (`SIGTRAP`) independent of the resource pressure; it now uses a two-hop redirect loop instead, matching the existing (previously unused) `/redirect-loop-a`/`/redirect-loop-b` fixture pattern.

### What is and isn't saved

Captured: rendered HTML and current DOM state, CSS, inline styles, images, favicons, web fonts, SVG, background images, `srcset` resources, same-origin frames, scripts needed for offline display, safe static GET responses, video poster images, the current values of non-sensitive form controls, a full-page screenshot, and extracted searchable text.

**Cross-origin frames** can't be read or safely archived, so rather than leaving a mysterious blank box (or an `<iframe>` still pointing at the live web), they're replaced with a marked placeholder naming the host the content came from. No `<iframe>` in an archived page ever points at a network address; the original URL survives only as an inert provenance attribute.

**Very tall pages** are screenshotted from the top down to 12,000 CSS pixels, and scaled down beyond that if the rasterized bitmap would still be too large. Real marketing pages are frequently 20,000–40,000px tall and Chromium simply refuses to rasterize a bitmap that size — a truncated screenshot is far more useful than the silent failure that produced no screenshot at all, and the extracted text still covers the whole page.

The capture budget is expressed in **device** pixels, not CSS pixels, because that is what Chromium actually allocates: a page is rasterized at the display's device pixel ratio, so on an ordinary 2× display a CSS-pixel budget silently permits four times as much memory as it names. Two limits apply to the rasterized bitmap — 16,000px in either dimension (Chromium's own texture ceiling is 16,384, past which the capture fails outright) and 32 million pixels in total, roughly 128 MB as a raw bitmap. The page is scaled to fit both. `fitCaptureToBudget()` is pure and unit-tested across the full range of page shapes and display ratios.

If the full-page capture fails anyway, a viewport screenshot is used so there is always *some* visual record — but the downgrade is **reported**, never silent: the Library records a `screenshot-viewport-only` warning on the archive, a site capture counts it as a warning on that page, and a run of consecutive downgrades during a crawl rebuilds the crawling view and is logged. An archive full of viewport crops that claims to hold full-page screenshots is a data-quality problem, not a cosmetic one.

**Never** saved: password-field contents, authentication headers, cookies, session tokens, API keys, payment or autofill data, sensitive hidden fields (CSRF tokens), private keys, or DRM-protected media. Fields whose name/id/autocomplete look credential-shaped are cleared as well, and credential-shaped URLs and content types are skipped outright. The crawl renders pages using your existing logged-in session so authenticated pages look right — but only the rendered output is stored, so a shared archive never carries reusable credentials. This is verified by a test that greps the entire container for the fixture's password and CSRF values.

### Image screenshot fallback

Normal downloading is always attempted first and always preferred, because it preserves the original file, resolution, animation, and vector properties. When an image *cannot* be stored normally — a cross-origin image that can't be downloaded, a `blob:` URL, a canvas whose pixels can't be serialized, a dynamically generated or blocked image — Archive Browser preserves what you actually saw by taking a **tightly cropped screenshot of the rendered element**.

The crop comes from the element's own `getBoundingClientRect()` scaled by the device pixel ratio, so it already accounts for CSS transforms, zoom, `object-fit`/`object-position`, cropping, and clipping, and it captures **only** the element's box — never surrounding text, account details, or form fields. The element is scrolled into view, layout and fonts are allowed to settle, and **your original scroll position is restored afterwards**.

A screenshot is *not* saved when the area is blank or fully transparent (checked by actually decoding the pixels via Electron's `nativeImage`, not by guessing from file size), when the element has zero size or was never rendered, when it's a tracking pixel (≤3px), or when it's a broken-image placeholder icon. In those cases the page shows a clearly styled **"Image unavailable in this archive"** placeholder instead. Any surrounding hyperlink is preserved either way.

Each screenshot-derived asset records its original URL (when known), page URL, element type, rendered and screenshot dimensions, capture timestamp, the reason normal saving failed, its content hash, and an explicit `isRenderedScreenshot` flag — so an archive never passes a screenshot off as the original file. These assets are deduplicated by content hash like any other.

Screenshot-derived images only preserve appearance at the displayed resolution. They do not retain original resolution, animation, embedded metadata, vector properties, transparency composited against the page, or hidden/offscreen portions of a cropped image.

### What can't be preserved

Perfect offline reproduction is not possible for every website, and the app doesn't claim it. Live search results, server-side forms, real-time feeds, multiplayer/collaborative features, live chat, continuously changing APIs, protected streaming media, DRM content, CAPTCHAs, payment flows, and anything requiring an active server session will not work in an archive. What an archive preserves is the content and navigation available at capture time. The full-page screenshot and extracted text remain available as durable fallbacks for every captured page.

## Forum capture (`Save Forum`)

A forum-aware capture mode on top of the `.sitearchive` machinery above, not a parallel system — the container format, checkpoint/resume, archive reading, offline link rewriting, and integrity hashing are all reused unmodified. What's new is scope-boundary logic for "just this forum," pagination handling, best-effort post extraction, and a persistent list of what's been saved.

**Three scopes**, chosen in the same Capture dialog as `current-page`/`entire-site`/`custom`:

- **This forum thread** (`forum-thread`) — every page of the thread's own pagination, nothing else. A link must belong to the same thread (`threadKeyOf()`, which collapses `?page=N`/`/page/N`/`&start=N` pagination shapes) to be followed; anything else is skipped as `skipped-out-of-forum-scope`.
- **This forum section** (`forum-section`) — the section's own pagination, plus every thread listed in it (and *that* thread's own pagination). Other sections are out of scope, same skip kind.
- **Entire forum** (`forum-whole`) — same-origin crawl like `entire-site`, but forum-aware: non-content routes (login/search/new-thread/reply/etc.) are still skipped via the existing `looksNonContent()`, now with an `includeProfiles` option so member/profile pages can be opted back in (off by default, matching the existing profile-skip behavior).

**Pagination is a first-class concept**, which the generic site-capture crawler didn't have: a link `looksLikeForumPagination()` (URL shape — `?page=`, `/page/N`, `&start=`/`&p=` — or link text like "Next"/a bare number) is enqueued at the **same depth** as the page that found it rather than depth+1, so a forum thread's `maxDepth` never truncates a long pagination chain — only actually entering a *different* thread or section costs a depth slot. A generous per-thread/section pagination-hop ceiling (500) is the actual trap guard, checked before the generic crawler-trap heuristic so a legitimate `?page=200` is never mistaken for a URL-generation trap.

**Forum-specific toggles** (all in `CaptureScope`, alongside the existing depth/pages/size/domain/media limits):

| Toggle | Default | Effect |
|---|---|---|
| `forumIncludeProfiles` | off | Follow links to member/author profile pages |
| `forumDownloadAttachments` | on | Download linked files (PDF, DOCX, ZIP, …) as assets — including ones with no file extension in the URL at all (`attachment.php?attachmentid=7`), detected by `looksLikeAttachment()` |
| `forumAttemptExternalImages` | on | Fetch images hosted on a different origin than the forum itself; when off, a cross-origin image gets the same screenshot-fallback treatment as any other image that can't be downloaded |

Print/alternate views of an already-reachable page (`?mode=print`, `/printthread.php`, …) are recognized by `looksLikePrintOrAlternateView()` and never crawled at all, regardless of scope — they'd just duplicate content already covered by the canonical URL.

**Posts, best-effort.** `forumPageScript.ts`'s `DETECT_FORUM_POSTS_SCRIPT` runs only on pages captured under a forum-* scope, looking for the `id="post-<n>"` / `id="post_<n>"` convention vBulletin, XenForo and phpBB all use (including this feature's own real-world test target). For each match it extracts author (nearest profile-shaped link or `.username`/`.author` class), timestamp (`<time datetime>`), post number, and body text, best-effort. **This is a heuristic, not a parser for any specific forum software** — a page with no matching markup contributes zero post entries and is still indexed at ordinary whole-page granularity via the ordinary `pages_fts` table, so search never silently loses coverage; it just doesn't get post-level precision for that page.

**Storage**: `ArchivedPageEntry` gains optional `forumThreadKey`/`forumSectionKey`/`forumPageIndex`; the manifest gains optional `forumPosts[]` and a `forumSummary` (section/thread/post/attachment/profile counts) present only on a forum-flavored capture. `index.sqlite` gains `forum_posts` (structured metadata) and a separate `forum_posts_fts` FTS5 table (`author`, `thread_title`, `section_title`, `url`, `body`) — a **post's own text**, not the whole page's, giving the precision "search by words from a post" needs. Post bodies are written to `posts/<hash-of-postId>.txt` during the crawl and read back once at finalize time, the same pattern `pages/<id>.txt` already uses to avoid holding a huge forum's worth of text in memory for the whole crawl.

**Search**: `OpenedArchive.searchForumPosts()` is a second FTS query alongside the existing page-level `search()`, surfaced in the same toolbar search panel as its own section (author + thread + section title + snippet) above the ordinary page results. Clicking a post result navigates to its page **and** its anchor — `navigateToPage`'s IPC gained an optional `anchor` parameter, appended as `#anchor` before `loadURL()`; the offline session's existing `rewriteLinks()` already preserves fragments on ordinary link clicks, so no new scroll-to-element code was needed, just the same fragment passed in from a different caller.

**Attachments as assets.** Anchors that look like a file download — `[download]`, or `looksLikeAttachment()`'s extension/path/query heuristics — are pulled into the same subresource-fetch pipeline images already use (`COLLECT_RESOURCES_SCRIPT` now also collects them, tagged `kind: 'attachment'`), gated by `forumDownloadAttachments`. The offline viewer's existing `rewriteLinks()` resolves the anchor to the local asset with no forum-specific code, since it already handles the general "captured asset" case.

**robots.txt**, added specifically for this feature (no site capture honored it before): fetched once per forum crawl at the start URL's origin, cached for the job's lifetime, and consulted alongside the existing scope check. Fails open — an unreachable or unparseable `robots.txt` never blocks a capture, matching ordinary crawler/browser behavior, so every fixture and site without one keeps working exactly as before.

**Saved Sites & Forums**: a new persistent, app-wide list of completed `.sitearchive` captures (🗂 in the toolbar) — separate from the Library, which only ever tracked single-page auto-captures. Backed by a small `site_archive_captures` table (`siteArchiveHistoryRepo.ts`), populated automatically when a capture/retry job completes and lazily backfilled when any `.sitearchive` is opened and not yet tracked (covers files captured before this feature existed, or moved/copied in from elsewhere). Each row shows scope, date, page/thread/image counts, size, and a clear **Incomplete** badge (sourced from the same `stopped-at-limit` failure entry the terminal progress dialog already renders — no new completeness-detection logic). "Remove" clears the registry row only; the file itself is never touched.

**A privacy note shown before every forum capture starts**, not conditional on any attempt to detect whether the content actually is private (there's no reliable signal for that): "If this content requires your account to view, sharing this archive could give them access to it too," gated by a required acknowledgment checkbox — the same pattern the dialog already uses for its over-limit confirmation. Credential stripping itself needs no forum-specific code: it's already generic (password fields, CSRF-shaped hidden fields, cookies, and auth headers are stripped/never captured regardless of what kind of page they're on — see "What is and isn't saved" above), so a forum's reply-box CSRF token is caught by the same mechanism a login form's password field already is.

**Testing**: `forumLinks.ts`'s predicates are pure and unit-tested (`tests/unit/forumLinks.spec.ts`, 28 tests), as is `addForumPost`/`forumSummary`/journal replay of forum posts and `searchForumPosts` (`tests/unit/forumArchive.spec.ts`, 5 tests) — both clean, alongside the full pre-existing 251-test unit suite (no regressions) and a clean `npm run typecheck`. End-to-end coverage (`tests/e2e/sitearchive-forum-capture.spec.ts`, 14 tests) extends the local forum fixture (`fixtures/siteServer.js`'s `forumRoute()` — now with real pagination in both the `?page=` and `/page/N` conventions, per-post markup, avatars, a shared emoji image, two attachment shapes, a genuinely externally-hosted image served from a second real origin, a broken image, a print-view duplicate, and a legacy alias URL) against all three scopes, pagination without depth exhaustion, attachment/avatar/external-image capture and the missing-image placeholder, forum-specific credential stripping, post search with anchor navigation, and the capture-history screen. The live `rangerovers.net` pass described in the roadmap entry below is manual/optional only, exactly as the project's testing philosophy requires — the fixture is what the automated suite actually depends on.

Building this surfaced two real crawler bugs, both fixed and reverified: a `maxDepth: 0` forum-thread capture originally never discovered its own page 2 at all, because the existing depth gate on calling `discoverLinks` at all (`item.depth < maxDepth`) ran before pagination's same-depth exemption could apply — fixed by moving the depth check to a per-link decision inside `discoverLinks` instead of the call site. Separately, `forum-section`'s "a thread discovered from a page in this section" rule was too loose — it let the fixture's ordinary global-nav links (Home, About, a product page) through as if they were threads, since it only checked "not the section's own pagination, discovered from a page in the section" without checking the link actually looked forum-shaped; fixed by also requiring the same leading path segment as the section itself (e.g. both under `/forum`).

**e2e-verified with a caveat, not fully automated-clean in this environment.** All 14 new e2e tests were driven to completion and their resulting archives inspected — 4 passed cleanly through Playwright end to end (credential stripping, post search + anchor navigation, both capture-history states); the other 10 produced a correct, fully-inspected archive (exact expected page/thread/section/asset counts, correct dedup, correct placeholders, correct skip records) but then hit a Playwright-worker `SIGSEGV` during the test's own assertion phase, consistently and reproducibly, in this ARM64 Linux sandbox -- the same class of resource-pressure crash already documented in Known Limitations and confirmed here via a live kernel OOM-kill log (`oom-kill:... task=electron`) on this same shared 3.8 GB-RAM machine. Every one of those 10 archives was independently re-verified correct via a standalone script driving `archiveReader.ts` directly (outside Playwright), confirming this is an environment constraint on the test harness, not a defect in the capture logic. `npx playwright test tests/e2e/sitearchive-forum-capture.spec.ts` should be re-run on a less memory-constrained machine (or CI) to get a clean automated pass; spot-checks of the pre-existing `sitearchive-forum.spec.ts` and `sitearchive-capture.spec.ts` specs (which exercise the same `discoverLinks`/`looksNonContent` functions this feature extends) showed no regressions, subject to the identical caveat.

## Progress feedback

Every operation that can take longer than a moment shows motion, so slow work never looks frozen:

| Operation | Feedback |
|---|---|
| Page loading in a tab | Spinner in the tab |
| Automatic background archiving | Toolbar indicator that pulses while pending, pulses faster while writing, pops once on success |
| Site capture | Determinate progress bar + elapsed clock + live counts + spinner on the current URL; indeterminate bar while zipping; full green bar when finished |
| Capture button while busy | Inline spinner, kept fully legible rather than dimmed out |
| Opening a `.sitearchive` | Full-surface busy overlay (it reads and checksum-verifies entries first) |
| Library search | Spinner; previous results stay visible so the grid doesn't blank on each keystroke |
| Archive details / Settings | Loading panel instead of an empty screen |
| Exporting an archive | Spinner on the button while zipping |

Two rules these follow: **never fake a percentage** — if the total isn't knowable, the bar is indeterminate; and **respect `prefers-reduced-motion`** — with that OS setting on, spinners and sweeps stop animating but every bar, count and label stays fully visible, so no information is lost, only the motion.

### Permissions

Websites get nothing by default. Each capability (notifications, geolocation, camera, microphone, MIDI, clipboard-read, display-capture) has a setting of **Deny**, **Allow**, or **Ask**; anything not on that list — USB, serial, HID, window-management — is refused outright with no way to enable it.

**Ask** shows a prompt naming the capability in plain language and the requesting origin (origin only, never a full URL, so a prompt can't leak a path). "Remember this choice" turns the answer into a standing default. There is no path where silence grants anything: an unanswered prompt auto-denies after two minutes, and if no window can display a prompt the request is denied rather than queued.

The pending-request registry lives in the main process with server-generated ids, and the only way to resolve one is the validated `permission:respond` channel from the trusted window. An unknown, stale, or already-used id is ignored, so a reply can't be forged or replayed to grant something that was never asked for.

### A note on dialogs and native views

Tab content is a native `WebContentsView` that the OS composites **on top of** this window's HTML. Any HTML dialog would therefore be painted *underneath* the live web page and be completely invisible, even though it is present and "visible" in the DOM. The app collapses the tab view to zero size whenever a modal is open ([App.tsx](src/renderer/App.tsx) `modalOpen`), which is what actually puts dialogs on screen.

This is worth knowing because DOM-level tests cannot catch a regression here — Playwright's `toBeVisible()` and `page.screenshot()` both ignore native-view occlusion. [tests/e2e/dialog-visibility.spec.ts](tests/e2e/dialog-visibility.spec.ts) asserts against the tab view's real bounds instead, and was confirmed to fail against the buggy version.

## Testing strategy and a real constraint

Tabs and the offline archive viewer are `WebContentsView` instances, not separate `BrowserWindow`s — Playwright's Electron support can only attach to real `BrowserWindow`s, so it cannot click into or read the DOM of a browsed or archived page directly. Two things work around this without weakening the app's own security boundaries:

- End-to-end tests drive the **trusted UI** (address bar, tab bar, Library, Settings) exactly as a user would, via Playwright's normal `Page` API against the one real `BrowserWindow`.
- For assertions that need to reach into a tab's content (e.g. simulating an SPA's `pushState` route change) or into main-process state (the capture catalog, settings, tab list), tests use [`src/main/testHooks.ts`](src/main/testHooks.ts) — a narrow object attached to `globalThis` **only** when `ARCHIVE_BROWSER_E2E=1` is set, reached via Playwright's `electronApplication.evaluate()`. It is never wired to any IPC channel, preload, or `contextBridge`, so it isn't reachable from any renderer or web content, and it doesn't exist at all in a normal run.

Tests run against local fixture websites ([fixtures/](fixtures/)) rather than the real internet, so nothing depends on a third-party site being up.

As of this build: **276 unit tests** and **148 end-to-end tests** (see Known Limitations for which of the most recent additions have and haven't been reconfirmed passing in this specific environment).

**Unit** (`tests/unit`, pure logic): URL resolution/validation and normalization, tracking-parameter stripping, same-origin scope checks, destructive-link and crawler-trap heuristics, atomic writes, path/ID validation, the IPC zod schemas, the SQLite catalog including FTS search and versioning, disk-space checks, settings persistence, domain-exclusion matching, the `.sitearchive` container round-trip, and its rejection of malformed and malicious archives (traversal in every form, zip bombs, bad manifests, checksum mismatches, future format versions).

## Packaging

Both package.json scripts and `electron-builder.yml` are already wired up. **These are unsigned local builds.** electron-builder can cross-package macOS and Windows targets from a single macOS machine (it ships its own macOS-native `makensis`/7-Zip tooling for the Windows installer, so nothing extra needs installing); Linux packages natively wherever it runs.

```bash
npm run package:mac        # fast unpacked .app in release/
npm run package:mac:dist   # unsigned .dmg + .zip (arm64 + x64) in release/
npm run package:win        # fast unpacked build in release/
npm run package:win:dist   # unsigned installer + portable .exe (arm64 + x64) in release/
npm run package:linux      # fast unpacked build in release/
npm run package:linux:dist # unsigned .AppImage in release/
```

Verified in this repo's own build environment (macOS, arm64 host):
- `npm run package:mac:dist` — produced `.dmg`/`.zip` for both arm64 and x64. The arm64 `.dmg` was mounted and the app inside launched successfully directly off the disk image, matching what a user double-clicking it would experience.
- `npm run package:win:dist` — produced `Archive Browser Setup 0.1.0.exe` (NSIS installer, one-click, bundles both x64 and arm64) and `Archive Browser 0.1.0.exe` (portable). Both are valid `PE32 executable (GUI) Intel 80386, ... Nullsoft Installer` files, and the underlying per-arch `.exe` binaries they contain are valid `PE32+` Windows executables for their target architecture. **Not actually run on a Windows machine** — none was available in this environment — so this is structural/build verification, not an execution test. See "Native module note" below for why this should work at runtime.

Verified separately, on this project's ARM64 Linux development sandbox:
- `npm run package:linux:dist` — produced `Archive Browser-0.2.0-arm64.AppImage`, a valid `ELF 64-bit LSB executable, ARM aarch64` file. **Actually launched** (`./*.AppImage --no-sandbox`, `--no-sandbox` only because this particular sandbox has no working setuid sandbox helper — not required on a normal Linux desktop) — the full real process tree came up (main process, GPU process, network service, renderers) and the app logged its normal startup sequence (`app.starting`, `database.opened`), the same as any other launch. This is the one platform in this list actually exercised end to end, not just built.

App icon: `build/icon.png` is a single 1024×1024 master image — electron-builder's icon convention finds it there by filename alone (no `mac.icon`/`win.icon` config needed) and converts it to every platform's native format itself: `.icns` for macOS, a multi-resolution `.ico` for Windows. Verified separately, on an ARM64 Linux host: `npm run package:mac` produced `Archive Browser.app/Contents/Resources/icon.icns` (`CFBundleIconFile` in `Info.plist` points at it) and `npm run package:win` produced and embedded a `.ico` into `Archive Browser.exe` via `rcedit` — confirmed by extracting the icon resource back out of the built `.exe` and checking it matched, not just that the build didn't error.

Native module note: `better-sqlite3` (the only native dependency) is built on N-API, which Node.js and Electron both guarantee is ABI-stable across versions — unlike older native addons, it does not need per-Electron-version rebuilding, and it already ships real prebuilt binaries for every platform/arch this app targets (`node_modules/better-sqlite3/prebuilds/*.node`, picked at runtime by its own loader based on `process.platform`/`process.arch`). `electron-builder.yml` sets `npmRebuild: false` accordingly — leaving it on makes electron-builder attempt a `node-gyp` rebuild instead of using those prebuilds, which is both unnecessary and fails outright when cross-packaging a Windows target from macOS (`node-gyp` can't cross-compile native modules from source). If a future native dependency isn't N-API-based and needs real per-platform compilation, cross-packaging from one machine stops being reliable and a per-OS CI build (e.g. a GitHub Actions matrix with `macos-latest` and `windows-latest` runners) becomes the correct approach instead.

**One real edge case this surfaced**: ABI-stable doesn't mean version-floor-free. `better-sqlite3@13.x` (and, separately, Electron 43 itself) require Node ≥22.12 to build/load at all -- an N-API build still needs the N-API level it was compiled against to actually be present in the Node runtime loading it, and a too-old Node doesn't necessarily fail that cleanly (see the Known Limitations entry on this below, where it manifested as a segfault rather than a clear version error). This is exactly why `package.json`'s `engines.node` and `.nvmrc` now both say `22.12+` rather than the `20+` an earlier pass of this README claimed.

### Public distribution (not done here)

- **macOS**: requires an Apple Developer ID certificate, `hardenedRuntime` entitlements, code signing, and notarization via `notarytool`. `electron-builder` supports this via `mac.notarize`/`CSC_LINK`/`CSC_KEY_PASSWORD` env vars once you have a certificate.
- **Windows**: requires a code-signing certificate (EV or OV) and `win.certificateFile`/`certificatePassword`, or a cloud signing service — otherwise SmartScreen will warn on every install.
- **Linux**: no code-signing equivalent blocks distribution the way macOS Gatekeeper or Windows SmartScreen do — an unsigned `.AppImage` just runs. Public distribution here is really about a stable download/update channel (the `publish` config already points at GitHub Releases, so `electron-updater`'s Linux support just needs a real release to check against) rather than a signing requirement to clear first.

macOS and Windows signing are deliberately left unconfigured; wiring them up is a roadmap item, not something to fake with a self-signed cert.

### Auto-update

[`electron-updater`](https://www.electron.build/auto-update) checks GitHub Releases (`publish` in `electron-builder.yml` — `owner: kevincalgary`, `repo: archivebro`) for a newer version, downloads it automatically once found, and waits for an explicit click before ever installing it:

- **Gated by two independent conditions, both required**: `settings.autoUpdateCheckEnabled` (on by default; a Settings toggle) AND `app.isPackaged` (false for every dev/test/e2e run). [`shouldAutoCheck()`](src/main/updates/updateService.ts) is the single, unit-tested function both the startup check and the periodic 4-hourly check consult — it is not possible for either to run without both conditions true.
- **A manual "Check for updates now" click bypasses the *setting*, never the packaging check.** An explicit click is its own consent regardless of whether automatic checks are on, but it still refuses to touch the network while unpackaged — confirmed end-to-end (`tests/e2e/updates.spec.ts`): calling it in this dev build resolves to a distinct `unsupported-dev` status rather than either attempting a request or silently no-opping.
- **Installing is never automatic.** `autoDownload: true` (so by the time you're told about an update, it's normally already there), but `autoInstallOnAppQuit: false` and `quitAndInstall()` is only ever called from the explicit "Restart and update" button (the Settings panel, or the banner shown app-wide once a download finishes) — never on a timer, and never just because the app happened to quit.
- **Surfaced three ways**: a Settings section (toggle, manual check button, live status text), an app-wide banner once a download completes, and — macOS only, matching platform convention — "Check for Updates…" in the app menu.

**What this hasn't verified, and can't yet, in this environment:** there is no actual published GitHub release for it to find, so the real download-and-install path has never run end to end — only the gating logic above (which is what determines whether it's *allowed* to run at all) is tested. **macOS specifically cannot work at all yet**: Squirrel.Mac (Electron's macOS auto-updater) refuses to run against an unsigned app, so this is genuinely blocked on the code-signing roadmap item, not just untested. Windows' NSIS-based updater and Linux's AppImage updater (`electron-updater` supports both) have no equivalent hard requirement, though an unsigned Windows installer still carries the existing SmartScreen warning either way.

### Dependency and Electron update cadence

Two workflows, covering the two failure modes of "we depend on something with a known vulnerability":

- [`.github/workflows/dependency-audit.yml`](.github/workflows/dependency-audit.yml) — **`npm audit --omit=dev` at `--audit-level=high` is a hard gate**, on every push/PR to `main` plus a weekly schedule (Monday 06:00 UTC) and `workflow_dispatch`. Only `dependencies` (never `devDependencies` — electron-builder resolves and bundles the production dependency subtree itself, confirmed by inspecting an actual packaged build's `app.asar`: no devDependency ever appears in it) ever reach a packaged build, so a high/critical advisory here fails the workflow. Clean as of this build: `npm audit --omit=dev` reports zero vulnerabilities. A second step runs a full `npm audit` (devDependencies included) informationally, not as a gate — also clean as of this build (`0 vulnerabilities`, full audit). The 10 advisories (2 critical) an earlier build of this README described here (transitive `devDependency`-only, via `@electron/rebuild`'s old `tar`/`make-fetch-happen` chain and `vitest`'s bundled `esbuild`/`vite`) are resolved: `@electron/rebuild` bumped `^3.7.0` → `^4.2.0` (the same major version electron-builder's own nested copy already used, so this was a same-behavior version-catch-up, not a functional change — reverified via a real `postinstall` rebuild of `better-sqlite3` and a real `package:linux` build afterward) and `vitest` bumped `^2.1.0` → `^4.1.11` (a genuine two-major-version jump, reverified by running the full 261-test unit suite clean afterward; the project's `vitest.config.ts` is minimal — no custom reporters or plugins — which is most of why this had no fallout). The weekly schedule (not just push/PR) is what makes this an actual cadence rather than a one-time check: it's what would catch a CVE disclosed against a version already sitting in `package-lock.json`, on a repo that might otherwise go untouched for weeks.
- [`.github/workflows/osv-scanner-pr.yml`](.github/workflows/osv-scanner-pr.yml) — Google's [OSV-Scanner reusable workflow](https://google.github.io/osv-scanner/github-action/), a second, independent advisory database (OSV.dev, not GitHub's), as a real gate on every PR. Unlike the informational full `npm audit` step above, this one is diff-based: it only fails on a vulnerability newly introduced by that PR, never on one of the pre-existing, already-accepted advisories — which is what makes it safe to run as a hard gate rather than informationally. Results also land in the repo's Security → Code scanning tab.

**Electron itself** is just a `devDependency` here (`node_modules/electron`), so both workflows above already cover it directly — a disclosed CVE against the pinned version surfaces the same way any other dependency's would, at the latest by the following Monday's scheduled `npm audit` run. The additional, Electron-specific policy: **bump to the latest stable release within one minor version** (i.e. don't let the pinned version fall more than one Electron minor behind current stable), checked manually against [Electron's releases](https://releases.electronjs.org/) rather than automated here, since a major bump is exactly the kind of change (native module ABI, deprecated API removal) this project has already hit real breakage from (see the "Fix Electron binary install and native-module ABI mismatch" commit) and shouldn't land without `npm test`'s full 387 tests passing against it first.

## Privacy and legal boundaries (by design)

Archive Browser does **not**: bypass authentication, paywalls, CAPTCHAs, DRM, or access controls; attempt to archive protected video streams; export cookies, passwords, authorization headers, session tokens, form entries, or localStorage secrets into an archive; capture password-field values; log keystrokes; send browsing history or archive contents to any server; or recursively crawl pages you didn't visit. Authenticated pages are archived only as the content currently rendered for the signed-in session — never with reusable credentials copied into the archive.

**The one disclosed exception**: an on-by-default, periodic check against GitHub Releases for a newer app version (see "Auto-update"). It carries no browsing history, archive contents, or any other user data — just "is there a newer Archive Browser release" — and a Settings toggle turns off the automatic/periodic version of it entirely.

Some sites cannot be preserved perfectly: pages that depend on live APIs, server-side sessions, streamed/DRM media, or service workers will render differently or not at all when viewed offline. The screenshot and extracted text are the durable fallback in those cases, and the offline viewer automatically falls back to them if the MHTML snapshot fails to render.

## Known limitations

- **MHTML rendering fidelity varies by site.** Pages relying on service workers, streamed media, or heavy runtime JS state may render imperfectly or fail entirely in the offline viewer; the screenshot/text fallback covers this case automatically, but it's a real fidelity gap, not a bug.
- **SPA "meaningful navigation" detection is a heuristic**, not a guarantee: hash-only changes with an unchanged pathname/search and title are treated as noise. Sites with unusual routing may occasionally under- or over-capture.
- **Multiple windows don't share a live tab list**, by design — each window's tabs, Library search, and Settings screen are independent panes onto the same underlying app state (one database, one settings file, one `.sitearchive` capture slot at a time app-wide). See "True multi-window support" in the roadmap below.
- **Disk-full handling is checked before a capture starts** (a free-space floor via `fs.statfs`), and a page/resource write that hits a suddenly-full disk mid-write is no longer an immediate permanent failure: `writeWithEnospcRetry()` ([diskSpace.ts](src/main/capture/diskSpace.ts)) retries an `ENOSPC` write with backoff (a few seconds' worth — long enough to smooth over a brief dip, short enough not to stall a whole crawl on one stuck write), and `addPage`/`addAsset`/`addResponse`/`addForumPost` in [archiveWriter.ts](src/main/sitearchive/archiveWriter.ts) all go through it. If the disk is still full once the retries are exhausted, the page is recorded with its own distinct `disk-full` failure kind and an actionable message, rather than the generic `render-failed`, and is retryable through the existing "Retry failed pages" flow once space has actually been freed. What this doesn't do: retry indefinitely or pause the crawl to wait for space — a disk that stays full is still a real failure for that page, just a clearly labeled and recoverable one instead of a mysterious one.
- **Developed and functionally verified on macOS, and separately on Linux.** `npm run dev`, `npm run build`, the full `npm test` suite (387 tests: 251 unit + 136 e2e — see the caveats just below for what's actually been reconfirmed most recently), and both `npm run package:mac` and `package:mac:dist` were actually run on macOS, including launching the packaged `.app` straight off the built `.dmg`. `npm run package:win:dist` was also run there (cross-packaged from macOS — see "Packaging") and produced a valid NSIS installer and portable `.exe`, but neither was *executed*, since no Windows machine was available in that environment. The Windows-specific code paths (accelerator strings, `%LOCALAPPDATA%`-style paths via `app.getPath`) use the same cross-platform Electron APIs exercised on macOS and are expected to work, but that's an expectation, not a verified fact, until someone runs the installer on real Windows. The archive-integrity-hashing, app-icon, CI-audit, auto-update, and parallel-crawling work above was separately built and the full suite (same count, growing alongside it) run again on ARM64 Linux each time, including a real X display for the e2e Electron windows. The search-inside-an-archive work (see "Searching inside an archive") is a partial exception: the full 198-test unit suite was reconfirmed clean, and its own dedicated e2e coverage (`sitearchive-parallel.spec.ts`, `sitearchive-search.spec.ts`) passed standalone, but a full e2e regression pass with search integrated was not cleanly completed in this environment — this ARM64 Linux sandbox is a real, shared, memory-constrained desktop (3.8 GB RAM, a live desktop session running alongside it), and repeated heavy Electron e2e runs during that session left it too resource-strained to trust a subsequent full-suite result. Root-caused to a genuine Node-version floor, not a memory-pressure flake: `better-sqlite3@13.x` and, separately, `electron@43` itself both require Node ≥22.12 (`npm install` said so plainly via `EBADENGINE` warnings once looked for), while this sandbox's system Node was 20.20.2 -- new enough that requiring the module doesn't error, old enough that the native binary segfaults the first time it's actually used, rather than failing cleanly. A same-major downgrade of `better-sqlite3` to the last Node-20-compatible release (12.11.1) was tried and rejected: its C++ source doesn't compile against Electron 43's newer Node headers at all, so that would have broken the real app to fix a test-only symptom. Fixed at the actual source instead: installed [nvm](https://github.com/nvm-sh/nvm) for this user account (no `sudo`, no change to the system's own `/usr/bin/node`, which every other process on this shared machine keeps using untouched) and Node 22.23.2 alongside it, added a project `.nvmrc` (`22`) and bumped `package.json`'s `engines.node` from the now-inaccurate `>=20` to `>=22.12.0` to match what the toolchain actually requires, then reinstalled `node_modules` under Node 22 (`0 vulnerabilities`, no more `EBADENGINE` warnings). Reverified clean afterward: the full 276-test unit suite and `npm run typecheck`, all 25 tests in `sitearchive-capture.spec.ts` including the two new allowlist cases, and `dialog-visibility.spec.ts` -- no segfaults, no flaky search-index warnings, on the same machine that couldn't get past the first `openSiteArchive()` call minutes earlier.

With that native-module fix in place, this pass ran essentially the **entire e2e suite** in this sandbox for the first time -- every spec file, not the individually-run subsets earlier passes were limited to. 146 of 148 tests passed, including several long-standing casualties: `completeness.spec.ts`'s cross-origin-frames test (previously died with a `SIGSEGV` regardless of unrelated code changes, confirmed above) passed cleanly, and all 14 of `sitearchive-forum-capture.spec.ts`'s tests passed end-to-end through Playwright itself (previously only 4/14 did, with the other 10 independently re-verified via a standalone script because of the same class of crash -- see "Forum capture" above). Running the full suite for real, rather than the subsets memory pressure had previously limited every pass to, also surfaced two genuine bugs neither unit tests nor a partial e2e run had caught:

- **The Settings "Automatic archiving" toggle didn't actually do anything.** `autoCaptureEnabled` was stored, exposed in the Settings UI, and validated by the IPC schema, but `CaptureService.capture()` never consulted it before scheduling a background capture -- only the per-tab "pause archiving" toggle and domain exclusions were ever wired to the real decision. Turning the setting off in Settings silently kept archiving every page anyway. Fixed with one more check alongside the existing per-tab-pause check in `captureService.ts`, and covered by a new e2e test (`exclusions-and-private.spec.ts`) that actually asserts nothing gets archived with the setting off, rather than only asserting the setting round-trips through Settings storage.
- **`sitearchive-parallel.spec.ts`'s two tests were flaky by construction**, not by environment: unlike every other capture test in the suite, they called `navigateViaAddressBar()` and immediately read `tab.url` to start a capture, without first waiting (`waitForTabs`) for the navigation to actually land -- so a capture occasionally started while the tab still read `about:blank`, failing with "Capture can only start from an http(s) page." Root-caused by temporarily instrumenting `testHooks.ts`'s swallowed capture-error path (normally collapsed to `null` for `awaitCapture()`) and rerunning with `DEBUG_E2E=1` (the flag that pipes the app's own main-process stdout/stderr into the test log -- easy to forget is off by default) to see the app's real log output instead of guessing from the test's own timeout. Fixed by adding the same `waitForTabs` wait every other capture test already does.

One test remains a proven environment artifact, not an app defect: `sitearchive-image-fallback.spec.ts`'s scroll-restore test failed with the page's scroll position reset to 0 after capture. Isolated by three successively narrower repros -- disabling the (at the time still-broken) `autoCaptureEnabled` setting, using the real per-tab pause instead, and finally removing capture from the scenario entirely (navigate, scroll, wait 4 seconds, do nothing else) -- and it still reset to 0 every time, on a page with no scroll-manipulating JS of its own. This is a rendering/compositor quirk of Chromium in this specific sandbox (no real GPU, `--no-sandbox`, software rendering), the same category as the `show: false` compositor bug already documented under "True multi-window support," not a bug in this app's capture or scroll-restore code, which the isolated repro never exercises at all. `sitearchive-retry.spec.ts` remains the one file that could not be gotten to a clean e2e pass here even after the native-module fix: its first test's Electron process reproducibly dies (`electronApplication.evaluate: Target page, context or browser has been closed`) moments after a real capture completes successfully (`capture.success` is logged immediately before the crash), and a concurrent memory sample during a failing run showed free memory drop from 863 MB to under 300 MB within four seconds -- consistent with the same resource-exhaustion class this file has hit on every previous pass (see above), not a new regression; its unit coverage (`retryableFailures`/`inferDepth`/`restoreFromManifest`) remains clean and unaffected.
- **`.sitearchive` pages are captured with a bounded parallel pool of workers** (`scope.concurrency`, 1–6 — see "Parallel crawling"), and *within* a page, subresources are fetched with their own bounded parallel pool (8 at a time), which together are what make real sites practical: on landrover.ca that's roughly 7s per page instead of ~50s, before accounting for the further speedup multiple concurrent pages provide.
- **SPA routes that use the History API are captured as the single rendered state** they were in at capture time. Hash routes are captured the same way. The crawler discovers links from the rendered DOM, so JS-created `<a href>` links are followed, but routes reachable only by clicking a JS handler (no real href) are not.
- **The "not captured" offline page signals its Open Live Version request via `document.title`**, because archived content deliberately has no IPC access. It works and is confirmed before anything opens, but it's a workaround rather than a clean channel.
- **A very long unlimited capture can still die mid-run, and the cause is not yet identified.** A full unlimited capture of `landrover.ca` ran 151 minutes, saved 810 pages and 2,818 deduplicated assets (2.6 GB staged, 6.8 GB downloaded before dedup), then the Electron process died with no output file. No crash report was produced and the app logged nothing for the whole run, so the mechanism is still unknown. Two things were ruled out by measurement: **disk space** (1.5 TB free) and **the archive builder's in-memory metadata** — `pages`, `assets`, `routes`, `queuedOrDone` and `failures` together hold ~26 MB at that scale, so spilling them into `index.sqlite` would not have helped. The screenshot budget fix above removes one plausible contributor (bitmaps of up to 41.4 megapixels, ~166 MB raw, were being requested against a cap that named 20 million) but is **not** demonstrated to be the cause. Per-page memory telemetry now exists (see "Per-page memory telemetry" above) — including whole-machine free memory, not just this process's own RSS, since "no crash report" is what an unblockable kernel out-of-memory kill looks like — and navigation now distinguishes a renderer dying mid-load from an ordinary timeout, so the next occurrence has both a trend and (if a renderer process died rather than the whole app) a named reason to look at. But the crash has not recurred or been reproduced in this environment, so the mechanism is still genuinely unknown.
- **Full-page screenshots degraded badly on that same run** — 693 of 810 pages fell back to a viewport crop, and after page 346 every remaining page did, 464 in a row with no recovery. The downgrade is now reported and a run of them rebuilds the crawling view, but *why* the renderer stopped being able to produce full-page captures, and never recovered across view recycles, is still unexplained.
- **Non-content routes are skipped by default**, but both a forum-* capture and Custom scope now have a way to opt specific ones back in. Sign-in, registration, search, and "new thread" routes are always excluded from crawls (see "Which pages a budgeted crawl spends itself on"); member/profile routes specifically can be opted back in for a forum-* capture via `forumIncludeProfiles` (see "Forum capture" above). Custom scope has the general equivalent: `CaptureScope.allowedNonContentPaths` (a list of path patterns, exposed as "Always include these paths" in the Custom scope dialog) is checked before `looksNonContent()`'s skip regexes in [urlNormalize.ts](src/main/sitearchive/urlNormalize.ts), and lets a link through if it matches. Matching is a deliberately simple case-insensitive substring match against the URL's pathname, not a full glob/regex engine — the same tradeoff `allowedDomains` already makes — so a typo fails safe (the link stays skipped) rather than silently matching everything.
- **Forum post detection is a heuristic** (see "Forum capture" above), keyed on the `id="post-<n>"` convention vBulletin/XenForo/phpBB all use. A forum running on different software, or a heavily customized theme with no such id, gets zero post-level search granularity — the page is still fully captured and searchable at ordinary whole-page granularity, it just doesn't get per-post author/timestamp/anchor precision.
- **The "current thread"/"current section" forum scope boundary uses URL-shape heuristics** (`threadKeyOf`/`sectionKeyOf`/leading-path-segment matching — see "Forum capture" above), not a parser for any specific forum software's URL scheme. A forum whose thread and section URLs don't share a distinguishing shape (e.g. no common `/forum`-style path prefix, or pagination that doesn't match `?page=`/`/page/N`/`&start=`) may under-capture a narrow scope's own pagination, or a "current section" capture may miss some of that section's threads. Nothing in this heuristic can cause a narrow scope to *over*-capture into a different thread or section — ambiguous links are excluded, not guessed at, by design.
- **Very large forums cannot be captured whole.** Discovery stops at 50,000 URLs and one archive is capped at 64 GB. A mid-sized vBulletin/XenForo forum (rangerovers.net: 114,229 threads, 917,167 posts) needs roughly 52,000 pages and, at measured rates, far more space and time than either ceiling allows. Capturing individual sections or threads works; capturing a whole forum of that size does not.
- **Images hotlinked to dead third-party hosts cannot be recovered.** Old forum posts overwhelmingly embed images from Photobucket, Flickr and similar, most of which stopped serving years ago. On one sampled photo thread, 60 of 116 images were already broken on the live site. Those become an explicit "Image unavailable in this archive" placeholder — the archive is honest about them, but the pictures are gone from the web, not merely un-archived.
- **Crawl ordering is fair, not smart.** Rotating the frontier across discovering pages stops any one page monopolising the budget, but it does not rank pages by how interesting they are. A budgeted capture gets a spread across the site's structure rather than the "best" pages, because the tool has no basis for judging which those are.
- **This is an MVP**: unsigned builds only, no auto-update.
- **The accessibility pass covers this app's own trusted UI, not archived page content.** Browsed and archived pages render in a native Electron `WebContentsView`, a separate surface this app doesn't own the markup of and that automated a11y tooling (axe via Playwright) can't attach to at all — a captured page is exactly as accessible, or not, as the original site was.

## Roadmap (post-MVP, prioritized)

~~A UI for recovering an interrupted capture~~ — **done.** See "Surviving an interrupted capture" above: a startup dialog offers Finish / Resume / Discard for every recoverable capture, backed by the same checkpoint/resume machinery, and tested end-to-end (`tests/e2e/recovery-ui.spec.ts`) including detection, each action, cancelling a discard, a capture with nothing to finish, a capture still running elsewhere, and relaunch behavior (an unresolved prompt reappears; a resolved one doesn't).

~~Per-page memory telemetry over a long crawl~~ — **instrumentation done, mystery still open.** See "Per-page memory telemetry" above: every page now logs main-process, crawling-renderer, and whole-machine memory, and view recycling logs the same readings right before tearing the view down. A later pass also closed a real blind spot in the same area: a renderer killed mid-navigation used to be indistinguishable from an ordinary page-load timeout, since nothing listened for `render-process-gone`; it's now its own retryable failure kind carrying Chromium's own reason (`oom`, `crashed`, `killed`, ...). What killed the original 151-minute crawl has *not* been identified — the crash hasn't recurred or been reproduced in this environment — but the next occurrence will have an actual trend, whole-machine memory, and a named per-page reason to look at instead of nothing.

~~Archive integrity hashing~~ — **done.** See "Per-page capture integrity" above: `page.mhtml`/`screenshot.png`/`text.txt` each get a SHA-256 recorded at capture time and verified on every read, matching what the `.sitearchive` container already did for its own entries. Tested at both the unit level (catalog round-trip, the migration adding the columns) and end-to-end (`tests/e2e/offline-viewing.spec.ts`: a tampered `page.mhtml` is refused and falls back with a distinct reason rather than being rendered).

~~Packaged app icons~~ — **done.** `build/icon.png` (1024×1024) is the single source electron-builder's icon convention expects; it converts that one file into every platform format itself (`.icns` for macOS, multi-resolution `.ico` for Windows) rather than needing per-platform art checked in. Verified in this environment: `npm run package:mac` produced `Archive Browser.app/Contents/Resources/icon.icns` with `CFBundleIconFile` pointing at it, and `npm run package:win` produced an `.ico` and embedded it into `Archive Browser.exe` via `rcedit` (confirmed by extracting the icon resource back out of the built exe) — both replacing Electron's default icon.

~~Dependency audit in CI~~ — **done.** See "Dependency and Electron update cadence" above: `npm audit --omit=dev` is a hard gate on every push/PR plus a weekly schedule (with a full `npm audit` reported informationally alongside it), a diff-based OSV-Scanner pass gates every PR against a second advisory database, and there's a documented (manual, checked-against-`releases.electronjs.org`) cadence for bumping Electron itself.

~~Auto-update~~ — **wired up, not end-to-end verified.** See "Auto-update" above: `electron-updater` checks GitHub Releases, gated by both a Settings toggle and `app.isPackaged` (unit-tested: `shouldAutoCheck()`), auto-downloads but never auto-installs, and is surfaced via Settings, an app-wide banner, and (macOS) the app menu. What isn't done: no real published release exists yet to test the actual download/install flow, and **macOS specifically cannot function until code signing (item 1 below) lands** — that's a hard technical requirement (Squirrel.Mac refuses to run unsigned), not just an untested path.

~~Parallel crawling~~ — **done.** See "Parallel crawling" above: `scope.concurrency` (1–6) now runs that many independent workers, each with its own hidden view, pulling from the same crawl queue. Making the crawl loop safe for real concurrency surfaced and fixed two genuine races (a `maxPages` check-then-act that could overshoot the page budget, and a `SiteArchiveBuilder.addAsset`/`addResponse` write race on identical concurrent content) — both covered by dedicated tests, and verified end-to-end that higher concurrency produces a real wall-clock speedup, not just a plumbed-through setting.

~~Search inside a `.sitearchive`~~ — **done.** See "Searching inside an archive" above: a `pages_fts` FTS5 table (title + extracted text) is written into `index.sqlite` at capture time, extracted to a temp file and queried by `OpenedArchive.search()` on open, and surfaced as a 🔍 button in the toolbar with live, debounced results that navigate the tab to the matched page on click. An archive from before this feature, or one with a corrupt catalog, still opens and browses normally — search just returns nothing.

~~Resume-only retry~~ — **done, e2e-unverified.** See "Resume-only retry" above: retrying a finished capture's failures now re-attempts only those pages and merges the result back into the same archive via `SiteArchiveBuilder.restoreFromManifest()`, instead of re-running the whole capture. Unit-tested (`retryableFailures`, `inferDepth`, `restoreFromManifest`) and typechecked clean; a dedicated e2e test exists but could not be confirmed passing in this environment — see the caveat at the end of that section and in Known Limitations.

~~Full-text search ranking/snippets~~ — **done.** See "Library search: ranking and snippets" above: the Library now orders matches by `bm25()` relevance (title weighted double) instead of the active sort, and attaches a plain-text snippet built from FTS5's `snippet(archives_fts, -1, ...)`, with the matched span highlighted via marker characters the renderer splits on rather than embedded HTML. Unit-tested (ranking order, snippet presence/absence) and verified end-to-end, including that a rendered Library card actually shows the highlighted term.

~~Export/import of the whole library~~ — **done.** See "Whole-library export and import" above: Settings → Data gains Export/Import buttons for the whole Library (not just one archive), as a single zip of every archive's catalog row plus its actual content files. Import treats the file as untrusted input the same way `.sitearchive` reading already does (path/size/zip-bomb validation, per-file checksum verification, per-entry shape validation), never overwrites an archive already present at the destination, and re-indexes extracted text into the destination's search. Unit-tested including a checksum-tampering case and a malformed-manifest case, and verified end-to-end across two genuinely independent app instances standing in for two separate machines.

~~Accessibility pass~~ — **done**, scoped to the trusted UI. Every dialog (Permission prompt, Capture scope, Capture progress, Recovery, Archive detail) shares one `useDialogA11y` hook: initial focus lands inside the dialog, Tab/Shift+Tab trap focus within it, Escape triggers whatever "cancel" already meant for that dialog, and focus is restored to the trigger on close. The tab strip is a roving-tabindex widget (Left/Right moves between tabs, Enter/Space selects, Delete/Backspace closes) rather than the ARIA `tablist`/`tab` pattern, which axe's `aria-required-children` rule rejects the moment a per-tab close button exists anywhere in a tab's subtree. Icon-only buttons and inputs that relied on visible glyphs or placeholders picked up real `aria-label`s, live regions (`aria-live`) cover async status text (Settings' "Saved" flash, update/library-transfer notes), and `--text-dim`/`--danger`/a new `--accent-solid`/`--danger-solid` pair were re-picked to clear WCAG AA contrast (4.5:1) everywhere they're actually used — solid button fills needed a darker shade than the border/focus-ring use of the same color. Regression-tested via `tests/e2e/accessibility.spec.ts`, which runs `@axe-core/playwright` (legacy mode — Electron's `BrowserWindow` can't support the CDP call the default cross-frame mode needs) against the browser screen, Library + archive detail, Settings, a permission prompt, and both capture dialogs, asserting zero serious/critical violations. **Out of scope**: archived/browsed page content renders in a native `WebContentsView` this app doesn't own the markup of and axe can't attach to — a captured page is exactly as accessible as the original site was, not more or less.

~~True multi-window support~~ — **done.** File → New Window (Cmd/Ctrl+N) opens an independent window with its own tab strip, address bar, Library, and Settings — tabs are per-window, matching every real browser, not shared or synced. Every `mainWindow`/`tabManager` that used to be a single hardcoded instance (IPC handlers, the app menu, `UpdateService`, permission-prompt routing) now resolves "which window" per call via a small registry (`src/main/windows/windowRegistry.ts`), keyed off which window actually made the IPC call (`BrowserWindow.fromWebContents(event.sender)`) rather than a fixed reference. A running `.sitearchive` capture no longer borrows a chrome window to host its crawling views at all: it renders on a dedicated window created once at startup (`captureHostWindow.ts`) that's never shown and never closed until the app quits, so closing the window that started a capture — or every open window — doesn't affect it. That hidden window is shown off-screen and inactive (`showInactive()` at `x/y: -10000`) rather than with Electron's `show: false`, because `show: false` was tried first and made full-page screenshots hang indefinitely partway through a crawl — Chromium's compositor for a window that has never actually been shown doesn't reliably produce frames, which is fatal for the CDP screenshot calls captures depend on. Each window's tabs are torn down (and its capture-service bookkeeping released) on that window's own `close`, and macOS no longer needs the old hide-instead-of-close hack — a window can be destroyed for real now that nothing else depends on that specific instance surviving; `window-all-closed` is likewise no longer used to decide when to quit, since the hidden capture-host window is itself a `BrowserWindow` and would keep that event from ever firing once a capture has run — each window's own `closed` handler checks the registry directly instead. Regression-tested via `tests/e2e/multi-window.spec.ts`: a second window opens with its own blank tab, tabs opened in one window never appear in another's list, closing one window leaves another fully functional, and a capture started in one window keeps running and completes after that window closes. **Known limitation, by design**: windows don't share a live tab list — see Known Limitations above.

~~"Save Forum"~~ — **done, e2e-verified with a caveat.** See "Forum capture (`Save Forum`)" above: three scopes (current thread / current section / entire forum) on top of the existing `.sitearchive` crawler, forum-aware link classification (pagination, attachments, avatars, print/alternate-view dedup, non-content skipping with an include-profiles opt-in), best-effort post extraction and search, a persistent Saved Sites &amp; Forums history list, and robots.txt support added specifically for this feature. Unit-tested (33 new tests, all passing) and typechecked clean, with no regressions in the pre-existing 218-test unit suite. All 14 new e2e tests were run to completion and their output archives verified correct (exact expected page/thread/section/asset counts, correct dedup, honest incomplete/placeholder reporting) — 4 passed cleanly through Playwright, the other 10 hit a resource-constrained Playwright-worker crash in this sandbox during their assertion phase (same documented class of crash as this file's other e2e-unverified entries, independently confirmed via a live kernel OOM-kill log on this same machine) but were re-verified correct via a standalone script reading the produced archive directly. Building this surfaced and fixed two real crawler bugs: a `maxDepth: 0` forum-thread capture originally never discovered its own page 2 (the depth gate on calling `discoverLinks` ran before pagination's same-depth exemption could apply), and `forum-section`'s "thread from this section" rule was initially loose enough to let ordinary site nav links through as if they were threads. The live `rangerovers.net` pass described in the original roadmap text was not attempted in this pass — the automated suite depends only on the local fixture, so this doesn't block marking the feature done, but a controlled manual run against it (public index → one section → one multi-page thread, respecting `robots.txt`, conservative rate, no sign-in/account actions) is still worth doing before fully trusting this against real-world forum software.

1. **Code signing + notarization** for macOS, code signing for Windows, so builds can be distributed publicly without OS warnings — and so auto-update can actually work on macOS at all.
2. **Run the built Windows installer/portable exe on real Windows hardware** and fix whatever that surfaces. Still blocked on producing that installer/portable exe at all in this environment: both targets compile through `makensis.exe`, a 32-bit x86 Windows binary, and this sandbox is ARM64 Linux with no `wine32` package available for that architecture at any layer (confirmed: installing `wine`/`wine64` and invoking it directly fails with "not supported on this system"). The unpacked `--dir` build (a real, verified PE32+ executable, both x64 and arm64) still works and was handed off as a zip for manual testing — needs real Windows, an x64 Linux box, or CI to produce the actual installer/portable artifacts.
3. **Run the live `rangerovers.net` manual/optional pass** described above, now that the feature itself is done — small controlled capture (public index → one section → one multi-page thread), respecting `robots.txt`, a conservative rate, and no sign-in/account actions.
